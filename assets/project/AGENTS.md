## Quality-code workflow

For any change affecting code, configuration, dependencies, tests, builds, data, releases, or agent behavior:

1. Read only the `MAP.md` sections relevant to touched files.
2. State observable acceptance criteria before implementation.
3. Replace bootstrap gaps in `MAP.md` and `TESTING.md`; ensure `.quality/quality.toml` profiles run the project's real tests and checks. `git diff --check` alone is not behavioral evidence.
4. Classify the highest actual product risk. An explicit higher-risk route in `.quality/quality.toml` cannot be downgraded. A routine local build, install, or version bump used only to deliver or confirm a change inherits the underlying change's risk.
5. **Low — builder only:** isolated copy, label, display text, comments, formatting, or static style with no behavior, data, accessibility, localization-contract, legal, billing, security, build, release, or agent-instruction effect. Make the smallest change and perform one focused visual, static, or targeted confirmation. Do not run the full suite, generate an audit packet, or start a subagent unless the user explicitly requests it or evidence raises the risk.
6. **Normal — contained behavior:** use proportionate test/fix loops, add or update the smallest relevant regression test, and run the smallest changed-scope verification that covers the behavior. Do not request an independent audit by default; do so only when the user asks or unresolved uncertainty raises the risk to high.
7. **High or critical — independent gate:** run the required higher verification profiles, generate `./quality audit-packet --criteria "<criteria>"`, and start a fresh agent with the audit skill (`$audit-code-change` in Codex or `/audit-code-change` in Claude Code). Once started, the audit remains exhaustive within scope.
8. Builder validation is mandatory in every lane. For a concrete bug, field-test the original or smallest failing case only as needed to understand it, then once to confirm the fix. Add more cases only when requested or justified by risk, an unclear cause, or inconsistent results.
9. Resolve blocking audit findings and request re-audit when an independent audit was required. Otherwise hand off after the lane's evidence passes, with residual risk stated when material.

## Efficient delegation and model selection

1. Preserve the risk lanes above. Task difficulty and product risk are separate: delegation may help difficult work, but cannot lower verification requirements or replace the independent audit. Low-risk work remains builder-only unless its stated exception applies.
2. Delegate a bounded subtask only when it can proceed independently and the expected benefit exceeds briefing, coordination, and integration costs. Keep small or tightly coupled work with the primary agent. Parallel execution may reduce elapsed time while increasing total token use; optimize expected completion cost, including retries and rework.
3. Use the runtime's native discovery tools, when exposed, to inspect currently accessible models, supported reasoning or effort controls, tools, context limits, and concurrency limits. Use available native capability metadata as evidence; refresh discovery when access or task requirements materially change, not before every spawn. Never invent model identifiers, capabilities, prices, or effort settings.
4. Choose the best supported fit from current evidence for the subtask's complexity, uncertainty, risk, context and tool needs, relevant skill requirements, and any user time or usage budget. Prefer the least costly option likely to meet acceptance criteria; a stronger model may be more efficient when it avoids retries. Do not hardcode providers, model names, rankings, or effort levels into this policy. Explicit user selections and higher-priority runtime constraints take precedence.
5. If discovery or model selection is unavailable, inherit the current model and supported defaults; use only advertised controls. If delegation itself is unavailable, perform permitted builder work locally. Do not claim optimal selection or weaken a required independent gate; report that gate as blocked if independence cannot be obtained.
6. Brief each helper with an observable outcome, relevant skill instructions and context, allowed file or read-only scope, dependencies, acceptance criteria, required evidence, and a concise result format. Give an independent auditor the raw scope and test basis without builder conclusions. Avoid copying unrelated history or sensitive data.
7. Size the team from ready work, not overall task size. Identify independently executable work units and dependencies; group small related units, assign useful work to the primary agent, and count only remaining units with enough value to justify a helper. Use native capacity/status tools or advertised metadata to check available slots, whether limits include the primary agent, active helpers, shared tool/resource constraints, and remaining budget. Choose the smallest useful helper count bounded by ready worthwhile units, available capacity, and affordable coordination/validation effort; those bounds are ceilings, not targets. Default to no implementation helpers when none qualify. Avoid duplicate investigations, overlapping file ownership, and automatic recursive fan-out; further delegation follows the same rules.
8. Spawn when a qualifying unit becomes ready and can overlap useful work; do not create idle helpers for future dependencies. Reuse suitable available helpers before starting new ones, except when independence requires a fresh agent. Reassess after completions, dependency changes, failures, or budget changes: add a helper only for another ready unit with expected net benefit, and stop or release redundant helpers using native lifecycle tools while preserving useful results. Continue useful independent work while helpers run and use native completion notifications or bounded waits instead of frequent polling. Schedule the required fresh audit after builder verification and budget for it separately; implementation helpers cannot satisfy that gate.
9. Increase model capability or supported effort when failed checks, ambiguity, or unreliable output show the current choice is insufficient. Do not spend repeated retries on the same ineffective approach or benchmark models for routine work. State the selection rationale and material discovery limitations briefly.
10. The primary agent owns integration and final validation. Helper completion is not proof of correctness. An agent that implemented or materially directed a change cannot supply its independent audit verdict.

For review, diagnosis, or planning, inspect and report without implementing. Ask before destructive actions, external writes, releases, purchases, or material scope expansion.
