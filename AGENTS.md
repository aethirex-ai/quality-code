## Shared quality foundation

Apply the selected standards once. Preserve project-specific instructions, user decisions, existing work and stricter risk, permission and verification requirements. Omitting a module never waives an existing project requirement. Set observable acceptance criteria before implementation. Distinguish evidence-backed defects from preferences and report uncertainty.

Verify the changed product behavior and disclose unavailable evidence. A build, score, screenshot, helper completion or generated audit packet is not an independent verdict. A builder or material implementation director cannot supply a required independent audit verdict. Resolve blocking findings and obtain the required re-review before claiming completion; unavailable required evidence remains BLOCKED. Never invent test results, legal claims, integrations, credentials, client relationships or savings.

For review, diagnosis, or planning, inspect and report without implementing. Ask before destructive actions, external writes, releases, purchases, or material scope expansion unless already authorized.

## Quality Code by AethDesign

## Quality-code workflow

For any change affecting code, configuration, dependencies, tests, builds, data, releases, or agent behavior:

1. Read only the `MAP.md` sections relevant to touched files.
2. State observable acceptance criteria before implementation.
3. Replace bootstrap gaps in `MAP.md` and `TESTING.md`; ensure `.quality/quality.toml` profiles run the project's real tests and checks. `git diff --check` alone is not behavioral evidence.
4. Classify the highest actual product risk. An explicit higher-risk route in `.quality/quality.toml` cannot be downgraded. A routine local build, install, or version bump used only to deliver or confirm a change inherits the underlying change's risk.
5. **Low — builder only:** isolated copy, label, display text, comments, formatting, or static style with no behavior, data, accessibility, localization-contract, legal, billing, security, build, release, or agent-instruction effect. Make the smallest change and perform one focused visual, static, or targeted confirmation. Do not run the full suite, generate an audit packet, or start a subagent unless the user explicitly requests it or evidence raises the risk.
6. **Normal — contained behavior:** use proportionate test/fix loops, add or update the smallest relevant regression test, and run the smallest changed-scope verification that covers the behavior. Do not request an independent audit by default; do so only when the user asks or unresolved uncertainty raises the risk to high.
7. **High or critical — independent gate:** run the required higher verification profiles, generate `./quality audit-packet --criteria "<criteria>"`, and start a fresh agent with the audit skill (`$audit-code-change` in Codex or `/audit-code-change` in Claude Code). Once started, the audit remains exhaustive within scope.
8. Builder validation is mandatory in every lane. For a concrete bug, field-test the original or smallest failing case only as needed to understand it, then once to confirm the fix. Add more cases only when requested or justified by risk, an unclear cause, or inconsistent results.
9. Resolve blocking audit findings and request re-audit when an independent audit was required. Otherwise hand off after the lane's evidence passes, with residual risk stated when material.

## Quality Visuals by AethDesign

This is a starting baseline for frontends and landing pages, not an exhaustive design system. Judge information, composition and usability, not whether a design was human- or AI-generated. User-approved brand and product requirements govern deliberate exceptions; do not invent an exception to retain filler.

### Content and composition

1. Give each page a specific audience, purpose and primary task. Explain the actual offer, service or product and its meaningful distinguishing details. Use real scope, coverage, indicative prices, constraints or evidence when available; do not invent business facts to fill a layout. Task screens prioritize the task rather than marketing copy. Make the offer or task understandable in the primary hierarchy; a tiny category label must not carry the explanation while the prominent headline stays interchangeable with unrelated businesses. Benefit-led or expressive copy is valid when concrete nearby content makes the offer clear.
2. Every section, sentence and visual treatment must add useful information, support a decision or action, or serve an intentional brand purpose. Remove content whose removal loses nothing useful. Do not default to a hero, reassurance strip, three cards, numbered process, FAQ and closing CTA regardless of the brief.
3. Do not add decorative uppercase slogan eyebrows above headings, illustrations or every section. A category, location or status label is appropriate only when it supplies necessary context. Remove repetitive reassurance, unsupported superlatives, generic slogans and tiny explanatory text that merely restates the heading. Authored UI prose must not introduce em or en dashes; use ordinary punctuation instead.
4. Use arrows and icons for meaningful actions, states or distinctions. Do not append arrows to every redirect or button, or give obvious labels decorative icons by default. Number only an actual sequence, ranking or reference. Do not invent numbered selling points to make a section look designed.
5. Choose the information structure before the container. Use cards for distinct selectable objects or meaningful comparisons, with useful content and proportionate dimensions. Prefer lists, rows, tables or plain sections where appropriate. Avoid half-empty rounded boxes, gratuitous bento grids, fake browser/device frames and multiple nested borders used as substitutes for hierarchy.
6. Use whitespace to group and prioritize content. Avoid inflated gaps, forced equal-height cards and oversized sections that make thin information appear substantial. Whitespace and asymmetry are valid deliberate choices when the composition supports them; visual density alone is not quality.
7. Give each CTA a clear action and an appropriate destination. Repeat it only where the visitor's progress justifies it. Do not add a large closing CTA section, moving slogan band, reassurance bar, FAQ or process panel merely to occupy space. A real process explanation must clarify decisions, timing, requirements or consequences.
8. Establish a coherent, business-specific visual direction through typography, imagery, layout and language. Use restrained readable hierarchy, relevant product views, photography, diagrams or intentional artwork. Avoid unrelated illustrations, floating promise badges, excessive italic emphasis and tiny tracked capitals. Decorative assets and motion need a purpose; honor reduced-motion preferences and do not obstruct operation.

### Full remakes and redesign intent

A request to fully remake or rethink a frontend authorizes reconsidering its information hierarchy, page composition, copy and visual system within the product scope. Preserve working capabilities, data, permissions, accessibility and explicit brand constraints; existing markup, section order, component shapes and decorative copy are candidates for replacement. A cleanup or reskin is appropriate only when that is the requested scope.

Before implementing a full remake, inspect the existing screens and establish a short design basis: the audience and primary decisions/tasks, verified product facts, weaknesses in the current hierarchy, and a proposed composition and visual direction grounded in those needs. Consider a materially different content/composition approach before choosing. Keep this proportionate and internal to the working evidence; do not add a planning ceremony or ask the user to design the page. When context is sparse, use repository/product evidence and state bounded assumptions instead of inventing business claims.

Rebuild the structure from the needed information and actions before choosing section templates or restyling existing containers. Decide what to remove, merge, reorder, replace or retain across the changed screens. A new palette, font, photograph, border radius or synonym headline does not by itself satisfy a full remake. Retain a familiar layout or usable interaction when the actual content/task supports it, and record the specific reason. Do not require arbitrary novelty, a fixed number of changed sections, unconventional navigation, extra features or unnecessary code churn.

Apply the baseline to the complete rendered composition, not only individual components. Look for repeated slogan-led headings, formulaic paired phrases, accent/italic words added by habit, tiny category labels, icon tiles, arrow suffixes, equal cards and three-step panels. Renaming, lowercasing or recoloring filler does not make it useful. These are review triggers, not proof of AI authorship or blanket bans on legitimate patterns. For each retained treatment, identify the information or interaction it contributes at that location; a generic claim that it adds polish, branding or consistency is insufficient. If a label is already clear, omit its ornamental arrow/icon; keep icons that communicate a distinct action, state or useful affordance. Decorative internal-link arrows are not justified merely because a click navigates.

Before handoff, compare the original and proposed full-page desktop/mobile views, including task screens. Explain the meaningful change in hierarchy/composition and remaining repeated patterns against the design basis. If the result keeps the old structure with primarily cosmetic substitutions and lacks a product-specific justification, continue redesigning before declaring the remake complete. A technically correct or cleaner result can still fail the requested design scope.

### Product completeness

9. Design mobile composition and content order intentionally, including realistic long and missing content. Provide semantic structure, clear form labels, readable contrast, visible keyboard focus, keyboard operation and comfortable touch targets. Prevent clipping, accidental overflow, unreadable supporting text and controls that become cramped at mobile widths.
10. Deliver working navigation and controls with clear loading, empty, validation, error and success states where applicable. Links have real destinations; buttons have real behavior. A polished happy-path screenshot does not establish a usable frontend. Keep marketing ornament out of login, forms and dashboards when it interferes with the task.
11. Provide accessible, accurate ownership/contact and privacy information and working relevant footer links. Identify the applicable jurisdiction, actual data handling and deployment context before deciding which legal notices or consent controls are needed. Use verified or owner-approved facts and text; never fabricate an address, registration, policy, testimonial, logo, statistic, certification or compliance claim. If required public-launch information is unavailable, report that launch requirement blocked. Clearly label fictional demonstrations without scattering repetitive demo disclaimers throughout the experience.
12. Verify appropriate page titles, metadata, assets, not-found behavior and reasonable loading performance for the actual product. Do not treat a legally incomplete footer, dead controls or missing required states as optional visual polish.

### Visual completion gate

For new pages/frontends and substantial visual redesigns, obtain a fresh independent visual review before claiming completion. Keep the existing code-risk lanes and required verification; low-risk isolated copy/static-style changes still receive one focused builder confirmation unless a stricter requirement or explicit review request applies.

With the toolkit available, declare this scope using `./quality audit-packet --visual --criteria "Observable visual and product outcomes"` and hand the packet and raw changed scope to the fresh reviewer. Instruction-only users provide the same scope, criteria and evidence directly. A packet is not a verdict; omitting a flag does not waive the selected visual gate.

Review representative desktop and mobile renders of every changed screen and relevant interaction/state, including full-page composition and realistic boundary content. Evaluate content usefulness, specificity, hierarchy, typography, spacing, imagery, responsive composition, accessibility, functional completeness and ownership/privacy requirements. A high average score cannot override a blocking finding. For a full remake, supply original and final renders plus the short design basis; the reviewer must test remake intent and cumulative pattern use, not just compliance with isolated prohibitions. Missing comparison evidence blocks that part of the gate.

Classify each finding against an observable baseline requirement, include the affected screen/viewport/state and evidence, and distinguish defects from subjective preferences. Unjustified filler, repetitive generic layouts, illegible or broken responsive states, dead controls and missing required disclosures/states must be corrected in scope. Re-render and recheck affected states; obtain independent re-review of blocking findings. Missing required render, interaction or independent review evidence is BLOCKED, never a presumed pass. Record remaining preferences and explicitly approved exceptions. Do not retroactively rewrite frozen benchmark outputs or scores when this baseline changes.

## Quality Swarms by AethDesign

## Efficient delegation and model selection

1. Preserve applicable project risk lanes and verification requirements. Difficulty and product risk are separate; delegation never lowers verification or replaces a required independent audit. Do not introduce helpers for small, low-impact work unless the user requests them or an applicable project requirement or concrete uncertainty justifies them.
2. Delegate only ready, independent work whose expected benefit exceeds briefing, runtime context, coordination and integration costs. Keep small or tightly coupled work local. Prefer direct delegation of a coherent outcome, with one owner for its implementation and focused checks, over splitting its markup, styling and simple interactions across agents. Parallelism may reduce time while increasing aggregate usage.
3. Discover accessible models, supported effort controls, tools, context limits and capacity through native tools or advertised metadata. Refresh when requirements/access change, not before every spawn. Select the least costly supported fit likely to meet acceptance criteria, considering uncertainty, risk, context, tools, skills and user budgets. Stronger capability can avoid retries; do not equate high effort with high quality for every task. Never invent or hardcode providers, model names, rankings, prices or settings. Explicit user choices and higher-priority runtime constraints prevail.
4. If discovery or selection is unavailable, inherit the current model and supported defaults and disclose the limitation. If delegation is unavailable, do permitted builder work locally; a required independent gate remains blocked until independence is available.
5. Size the smallest useful team from ready worthwhile units, available native capacity (including the primary and all descendants), resource ownership and remaining budget. Assign useful work to the primary. Ceilings are not targets. Avoid overlapping ownership, duplicate investigations, idle helpers and automatic fan-out. Reuse a helper while its context remains relevant; otherwise use a fresh scoped brief or supported compaction.
6. Brief each helper with outcome, acceptance criteria, applicable safety/risk/skill instructions, allowed files/tools/data, contracts/dependencies, budget and required evidence. Use applicable instructions already supplied by the runtime; re-read them only to resolve missing or stale details. Reference source files instead of pasting their contents or unrelated history. Request a concise return: changed paths, check results, unresolved issues and decisions needed. Independent auditors receive fresh raw scope/test basis without builder conclusions.
7. Spawn when the unit can overlap useful primary work. Use completion events or bounded waits; communicate at dependency changes, blockers and meaningful milestones. Inspect a helper's changed scope and evidence instead of repeating its entire investigation or every passing check. Re-run checks needed for integration, failures or required gates; primary ownership of validation never disappears.
8. Escalate capability or supported effort when ambiguity, failed checks or unreliable output justify it; avoid repeated ineffective retries. State the rationale and material discovery limitations briefly. An agent that implemented or materially directed a change cannot supply its independent audit verdict.

## Cost-aware implementation ownership

1. Separate product verification risk from each work unit's implementation difficulty and review needs. A critical application retains its critical gate; that label alone does not require the strongest model for every implementation step. Keep security architecture, authorization contracts and integration with a qualified owner; a bounded implementation may use a cheaper qualified owner with focused checks and appropriate review.
2. Before assigning a substantial bundle to the default or a more costly model, check whether it contains worthwhile independent implementation outcomes with explicit interfaces and observable acceptance checks. Examples include contract-defined validation, data mapping, catalogue operations, fixtures or library integration. Separate decisions from mechanical implementation only when the handoff saves expected total work; preserve coherent ownership and continuous visual direction. Do not fragment tightly coupled files or create work merely to use a cheaper model.
3. For each worthwhile outcome, compare an accessible lower-cost candidate with the selected model using native capability/tool evidence and available cost evidence. Prefer the cheaper qualified candidate for bounded implementation and its focused tests. A whole-project risk label, a broad frontend/backend label or a generic catalogue description is insufficient by itself to reject it: identify a concrete complexity, tool, context or reliability requirement, relevant failed check, or why no useful smaller outcome exists. Include expected briefing, review, retries and integration in the comparison. If cost or capability evidence is missing, disclose uncertainty rather than inventing a ranking or forcing a cheap-model trial.
4. Use the native controls that actually support model/effort selection. If a full-history fork inherits settings or rejects overrides, use fresh scoped context when supported; otherwise inherit and report the limitation. Record requested settings separately from observed native settings; if observation is unavailable, say unknown. For substantial delegation, retain a compact routing note with outcome, candidates, selection/rejection reason, requested/observed model and effort, and check/escalation evidence. Lower effort on the same model is not cheaper-model delegation. No minimum helper count or cheaper-model share is required; escalate on concrete uncertainty or failed checks while preserving all gates.

## Bounded swarms and scoped context

1. Direct delegation is the default topology. Add a workstream lead only when it has substantial useful work and a ready independent child whose expected benefit exceeds an additional runtime context and handoff. A lead owning a small page or module should normally finish its simple styling/interactions itself. Do not manufacture recursion to exercise a swarm feature.
2. The primary owns one shared budget across the entire tree for active agents, elapsed time, reported usage, retries, transferred context, integration and verification across the entire tree. Branch shares are allocations, never fresh allowances. Reserve time/capacity/usage for integration and required audit; explain further-spawn boundaries to each lead. Reconcile at meaningful progress events and respect native enforcement. Exact usage unavailable means conservative qualitative allocations and disclosed uncertainty, never invented token/subscription conversions.
3. Before any descendant spawn, check ready work, branch/global budget, capacity and ownership through native status or the primary. Do not fill all slots with leads waiting on children. Serialize, reuse/release supported capacity or work locally when bounds are reached. Stop expansion when duplication, coordination or rework exceeds benefit. Lower API prices do not establish lower subscription consumption.
4. Pass the smallest sufficient task brief and context and prefer a fresh task-scoped session when supported. Load precise file sections and contracts as needed; preserve safety, permissions, risk and audit constraints. Do not forward full transcripts, repeated tool logs, unrelated siblings or credentials. Keep large/generated/binary data out of textual returns: use native image/media presentation and file references, summarize result metadata, and never print base64 or a complete media-tool result merely to find its saved path. Bound routine command output and narrow searches before reading entire files.
5. Distinguish supplied context from model context capacity. Configure a smaller window/input limit only through explicitly supported controls and only when it fits required evidence, reasoning, tools and output. Otherwise reduce supplied history/retrieval; do not invent window settings or promise savings. Track aggregate input, cached input and output separately when native telemetry supports it, without double-counting subsets. Stop/replan on budget pressure; retain acceptance and gate requirements.

## Visual and code-heavy workload ownership

1. Classify each ready outcome by visual coupling and code complexity; frontend/backend labels alone do not determine topology. Keep visually coupled work with one persistent design owner responsible for visual direction, shared styles/components, content rhythm and final desktop/mobile composition. Use only a small useful set of helpers for bounded independent outcomes; do not swarm across the markup, styling and interactions of the same experience.
2. For substantial code-heavy work, use a bounded swarm only when ready independent outcomes, explicit contracts, resource ownership and the shared budget justify it. Prefer coherent direct owners; hierarchy still requires substantial useful work at each level. Coupled or small work remains local. Model/effort selection uses native evidence and the least costly qualified fit, escalating on concrete uncertainty or failures; never hardcode models or treat cheaper ownership as equivalent quality.
3. In mixed applications, keep continuous ownership of visual direction and integration while delegating worthwhile independent coding work. Agree API/data/state contracts before overlapping work. Validate the integrated user journeys, permissions, state transitions and persistence through navigation/reload, plus representative rendered states. A passing backend test does not prove frontend behavior or visual consistency, and a polished interface does not prove backend correctness. Preserve risk lanes and independent gates.
4. When measuring delegation, retain observed failed checks, corrections and targeted rechecks. Distinguish distinct product defects, visual refinements, tooling errors, expected construction/negative failures and duplicate manifestations; missing evidence is unknown. Count evidenced fix/recheck cycles separately from check reruns or model turns, include their usage/time in the shared budget and report unresolved final errors.

## Quality at delegation boundaries

1. Give each owner observable product checks, not merely a file list. For presentation work, communicate audience, intended visual identity, content/imagery accuracy, typography, readable contrast, mobile composition, form ergonomics and accessible interactions. Inspect representative rendered desktop/mobile states before handoff when tools permit; a passing build or DOM check does not prove visual quality. Report blocked visual verification explicitly and preserve required independent review.
2. For diagnosis, require concrete reproductions tied to contracts, distinguish defects from preferences, include boundary/negative cases and healthy controls, and report uncertainty. For fixes, confirm the failing behavior and relevant regressions; do not treat more findings, more tests or helper completion as proof of quality. The primary integrates and validates the final experience and its contracts.
