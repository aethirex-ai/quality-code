Build ServiceFlow, a polished, full-stack MVP for one fictional local home-services business, suitable as an AethDesign software-development and UI/UX portfolio demonstration for potential Upwork clients. AethDesign is a software-development and UI/UX design studio, not the service business. The actual studio reference is https://www.aethdesign.com/ and the supplied frozen BRAND references. Do not imply a real client relationship or invent real company/customer claims.

Inspect this repository and its instructions first. Preserve existing work. Follow the supplied Quality Code standard, its risk lanes, continuous visual ownership and model/delegation discovery rules. The fixture is a clean project, not a previous implementation. Use a maintainable TypeScript web stack, responsive frontend, relational database and mature authentication library. Do not roll your own password/session system. Make the project locally runnable with migrations, seeded demo data and no paid services or secrets. Dependencies may be installed from the permitted public package registry. Do not put keys in client code or commit secrets.

Scope: one business, three roles. Customer submits service requests and can view only their own requests. Provider manages requests assigned to this business. Admin can manage all requests and the service catalogue. Seed two distinct customers (needed to verify ownership), one provider and one admin with documented login details. Do not add multi-tenant organizations, payments, live scheduling, automatic matching, SMS, real email sending, uploads or a marketplace.

CUSTOMER EXPERIENCE
1. Public landing page explaining the fictional service business, with a clear Request a service action.
2. Small seeded catalogue with useful descriptions and indicative prices or Request a quote.
3. Signed-in request form: service, short work description, postcode/location, preferred date or date range (not confirmed appointment), contact name and phone/email.
4. Client and server validation; useful success, error, loading, empty and validation states.
5. Customer dashboard with own requests and current status. Direct routes and API calls must not expose another customer's requests.

PROVIDER AND ADMIN
1. Protected dashboard with totals by status, recent enquiries and searchable/filterable request list.
2. Detail includes supplied information, service, date preference, status and chronological history.
3. Server-enforced workflow: New -> Reviewing -> Quoted -> Booked -> Completed. Declined is allowed from New, Reviewing or Quoted; Completed and Declined are terminal. Declining a booked request is outside this MVP. Explicitly reject skips, reverse moves and stale conflicting updates, and do not record rejected mutations as successful actions.
4. Provider manages requests; only admin can create/edit/activate/deactivate/delete services. Prevent deletion of a referenced service or use an explicit historical-preserving deletion policy; inactive/deleted services cannot be selected for new requests. Historical requests must remain intelligible.
5. Persist status changes and relevant actions with actor and timestamp, atomically with the corresponding mutation. Customer can read history for their own requests only.

AI-ASSISTED RESPONSE
Authorized provider/admin sees Draft reply on request detail. Produce a concise customer-facing reply using only request details and selected service, plus at most three useful questions for missing information. Draft is editable, labeled as AI-generated or deterministic demo-generated as applicable, and never sent automatically. Clearly require review; do not claim contact has occurred. The benchmark runs entirely without an AI key, using a clearly labeled deterministic server-side fallback. Implement a separate server-side configured provider adapter reading its key and settings from environment variables, with the deterministic fallback when no key is configured. Require mocked tests for the configured adapter path; do not request credentials or make live AI requests. Exclude unnecessary contact/personal data from model payloads and never log secrets. Customers cannot use this staff action or access another customer's details through it. Drafting alone does not change request status or record a sent message.

DATA AND SECURITY
Relational users/roles, services, requests and activity; migrations and seed script. Mature authentication library. Server-side authorization for every read/write and draft action, not only hidden controls. Normalize/validate inputs server-side and render untrusted content as text. Safe user errors, no stack traces/secrets. Protect unauthenticated/unauthorized mutations and cross-site requests using the stack's established mechanisms. Sample data only. State and history must survive navigation, reload and server restart. Avoid duplicate committed writes on retry or refresh failure. No external live integrations.

Calm professional local-service visual system and useful dashboard hierarchy; no unstyled scaffold. Keep one persistent owner of visual direction and integration. Reusable components, typed contracts and separation of UI/business/persistence/AI logic. No dead buttons, placeholder links, fabricated integrations or silent failures. Supply .env.example placeholders and exact setup/install/migrate/seed/run/test/build commands in README, with demo accounts and limits. Focused tests for validation, ownership/roles, transitions, service permissions/history preservation and AI fallback and configured-adapter mocks. Add real end-to-end customer submission/provider-update coverage using the available browser tooling. Inspect actual desktop/mobile renders and user journeys; metadata or a passing build alone is insufficient.
