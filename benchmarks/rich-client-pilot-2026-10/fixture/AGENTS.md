## Quality-code workflow

For any change affecting code, configuration, dependencies, tests, builds, data, releases, or agent behavior:

1. Read only the `MAP.md` sections relevant to touched files.
2. State observable acceptance criteria before implementation.
3. Replace bootstrap gaps in `MAP.md` and `TESTING.md`; ensure `.quality/quality.toml` profiles run the project's real tests and checks. `git diff --check` alone is not behavioral evidence.
4. Classify the highest actual product risk. An explicit higher-risk route in `.quality/quality.toml` cannot be downgraded. A routine local build, install, or version bump used only to deliver or confirm a change inherits the underlying change's risk.
5. **Low — builder only:** isolated copy, label, display text, comments, formatting, or static style with no behavior, data, accessibility, localization-contract, legal, billing, security, build, release, or agent-instruction effect. Make the smallest change and perform one focused visual, static, or targeted confirmation. Do not run the full suite, generate an audit packet, or start a subagent unless the user explicitly requests it or evidence raises the risk.
6. **Normal — contained behavior:** use proportionate test/fix loops, add or update the smallest relevant regression test, and run the smallest changed-scope verification that covers the behavior. Do not request an independent audit by default; do so only when the user asks or unresolved uncertainty raises the risk to high.
7. **High or critical — independent gate:** run the required higher verification profiles, generate `./quality audit-packet --criteria "<criteria>"`, and start a fresh agent with the audit skill (`$audit-code-change` in Codex or `/audit-code-change` in Claude Code). Once started, the audit remains exhaustive within scope.
8. Builder validation is mandatory in every lane. For a concrete bug, field-test the original or smallest failing case only as needed to understand it, then once to confirm the fix. Add more cases only when requested or justified by risk, an unclear cause, or inconsistent results.
9. Resolve blocking audit findings and request re-audit when an independent audit was required. Otherwise hand off after the lane's evidence passes, with residual risk stated when material.

## Efficient delegation and model selection

1. Preserve the risk lanes above. Difficulty and product risk are separate; delegation never lowers verification or replaces a required independent audit. Low-risk work remains builder-only unless its stated exception applies.
2. Delegate only ready, independent work whose expected benefit exceeds briefing, runtime context, coordination and integration costs. Keep small or tightly coupled work local. Prefer direct delegation of a coherent outcome, with one owner for its implementation and focused checks, over splitting its markup, styling and simple interactions across agents. Parallelism may reduce time while increasing aggregate usage.
3. Discover accessible models, supported effort controls, tools, context limits and capacity through native tools or advertised metadata. Refresh when requirements/access change, not before every spawn. Select the least costly supported fit likely to meet acceptance criteria, considering uncertainty, risk, context, tools, skills and user budgets. Stronger capability can avoid retries; do not equate high effort with high quality for every task. Never invent or hardcode providers, model names, rankings, prices or settings. Explicit user choices and higher-priority runtime constraints prevail.
4. If discovery or selection is unavailable, inherit the current model and supported defaults and disclose the limitation. If delegation is unavailable, do permitted builder work locally; a required independent gate remains blocked until independence is available.
5. Size the smallest useful team from ready worthwhile units, available native capacity (including the primary and all descendants), resource ownership and remaining budget. Assign useful work to the primary. Ceilings are not targets. Avoid overlapping ownership, duplicate investigations, idle helpers and automatic fan-out. Reuse a helper while its context remains relevant; otherwise use a fresh scoped brief or supported compaction.
6. Brief each helper with outcome, acceptance criteria, applicable safety/risk/skill instructions, allowed files/tools/data, contracts/dependencies, budget and required evidence. Use applicable instructions already supplied by the runtime; re-read them only to resolve missing or stale details. Reference source files instead of pasting their contents or unrelated history. Request a concise return: changed paths, check results, unresolved issues and decisions needed. Independent auditors receive fresh raw scope/test basis without builder conclusions.
7. Spawn when the unit can overlap useful primary work. Use completion events or bounded waits; communicate at dependency changes, blockers and meaningful milestones. Inspect a helper's changed scope and evidence instead of repeating its entire investigation or every passing check. Re-run checks needed for integration, failures or required gates; primary ownership of validation never disappears.
8. Escalate capability or supported effort when ambiguity, failed checks or unreliable output justify it; avoid repeated ineffective retries. State the rationale and material discovery limitations briefly. An agent that implemented or materially directed a change cannot supply its independent audit verdict.

## Bounded swarms and scoped context

1. Direct delegation is the default topology. Add a workstream lead only when it has substantial useful work and a ready independent child whose expected benefit exceeds an additional runtime context and handoff. A lead owning a small page or module should normally finish its simple styling/interactions itself. Do not manufacture recursion to exercise a swarm feature.
2. The primary owns one shared budget across the entire tree for active agents, elapsed time, reported usage, retries, transferred context, integration and verification across the entire tree. Branch shares are allocations, never fresh allowances. Reserve time/capacity/usage for integration and required audit; explain further-spawn boundaries to each lead. Reconcile at meaningful progress events and respect native enforcement. Exact usage unavailable means conservative qualitative allocations and disclosed uncertainty, never invented token/subscription conversions.
3. Before any descendant spawn, check ready work, branch/global budget, capacity and ownership through native status or the primary. Do not fill all slots with leads waiting on children. Serialize, reuse/release supported capacity or work locally when bounds are reached. Stop expansion when duplication, coordination or rework exceeds benefit. Lower API prices do not establish lower subscription consumption.
4. Pass the smallest sufficient task brief and context and prefer a fresh task-scoped session when supported. Load precise file sections and contracts as needed; preserve safety, permissions, risk and audit constraints. Do not forward full transcripts, repeated tool logs, unrelated siblings or credentials. Keep large/generated/binary data out of textual returns: use native image/media presentation and file references, summarize result metadata, and never print base64 or a complete media-tool result merely to find its saved path. Bound routine command output and narrow searches before reading entire files.
5. Distinguish supplied context from model context capacity. Configure a smaller window/input limit only through explicitly supported controls and only when it fits required evidence, reasoning, tools and output. Otherwise reduce supplied history/retrieval; do not invent window settings or promise savings. Track aggregate input, cached input and output separately when native telemetry supports it, without double-counting subsets. Stop/replan on budget pressure; retain acceptance and gate requirements.

## Quality at delegation boundaries

1. Give each owner observable product checks, not merely a file list. For presentation work, communicate audience, intended visual identity, content/imagery accuracy, typography, readable contrast, mobile composition, form ergonomics and accessible interactions. Inspect representative rendered desktop/mobile states before handoff when tools permit; a passing build or DOM check does not prove visual quality. Report blocked visual verification explicitly and preserve required independent review.
2. For diagnosis, require concrete reproductions tied to contracts, distinguish defects from preferences, include boundary/negative cases and healthy controls, and report uncertainty. For fixes, confirm the failing behavior and relevant regressions; do not treat more findings, more tests or helper completion as proof of quality. The primary integrates and validates the final experience and its contracts.

For review, diagnosis, or planning, inspect and report without implementing. Ask before destructive actions, external writes, releases, purchases, or material scope expansion.
