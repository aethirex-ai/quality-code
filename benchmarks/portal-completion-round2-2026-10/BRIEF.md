Port0 is permitted and must print one JSON readiness line `{"ready":true,"port":ACTUAL_PORT}` to stdout after initialization/binding, flushed. Serve `/` and local static assets from `public/`, all APIs below. Never bind outside loopback. `--db` may point to a new file: initialize the exact seed below once, then retain existing data on restart. No singleton fixed global DB/port or hardcoded fixture folder. Use JSON for APIs, integer cents, appropriate status codes, bounded input and SQLite atomic mutations. Avoid raw tracebacks/secrets in responses or arbitrary file serving. Normal request logs go to stderr. No external dependencies/services, actual personal data, uploads/email/checkout. This is a synthetic localhost exercise; independent gates remain required before external release.

## API contracts (same for both sessions)
Success bodies JSON; error shape `{"error":{"code":"...","message":"..."}}`, useful strings. Malformed JSON/incorrect field types/invalid lengths/whitespace-only required text are400, never500/partial mutation. Unknown project404. No session401 on protected APIs; wrong-client project access404 without data. Unauthorized staff actions403. Client roles cannot be changed via submitted body/cookie. No permissive CORS.

- GET `/api/projects/:id/revisions`:200 {revisions:[{number,title,summary,publishedAt},...]}, chronological increasing number. POST same path staff-only {expectedRevision:N,title,summary}: expectedRevision integer>=1 and equal currentRevision; title trimmed1..120chars, summary trimmed1..2000. Success201 {revision:{number:N+1,title,summary,publishedAt},project:{id,status:"awaiting_review",currentRevision:N+1,...}}. Atomic insert/update/event: stale expectedRevision409, no added revision or audit event. Publishing after approved/changes_requested opens the new review. Preserve older revisions/decisions. Two competing writes for the same expected revision yield exactlyone201 and one409, never duplicate number.
- POST `/api/projects/:id/decision`: owner client only (staff403), {revision:N,decision:"approve"|"request_changes",note:string}. ## Composed failure paths and recovery acceptance

Validate before hashing/encoding/database work. Guard every asynchronous response/continuation against changed account/navigation state, including conflict/error-recovery refetches. Exercise a delayed old-account conflict refresh overlapping logout/login as another client; no old project or identity may appear. Distinguish successful persisted mutations from a subsequent failed refresh: acknowledge the save, preserve correct UI recovery and prevent duplicate retry of that acknowledged submission. Field-test these combined paths with healthy controls, not only independent normal flows. Exactly-one event/state contracts still apply.
